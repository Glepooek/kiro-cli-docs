# 思考工具

思考工具使 Kiro 能够在处理复杂问题时展示其推理过程，提供结论如何达成的透明度。

## 概述

启用后，思考工具允许 Kiro 将复杂推理分解为可见的步骤，帮助您理解决策过程并从 AI 的问题解决方法中学习。

## 启用思考工具

```bash
kiro-cli settings chat.enableThinking true
```

或使用实验命令：

```bash
/experiment
# 从列表中选择 "Thinking"
```

## 工作原理

当 Kiro 遇到需要多步骤推理的复杂问题时，它会：
1. **展示思考过程** 在处理问题时
2. **分解推理** 为逻辑步骤
3. **解释中间结论** 在得出最终答案之前
4. **使决策透明** 以便您可以跟随

## 何时出现思考

思考工具在以下情况下由 Kiro 自动调用：
- **复杂问题解决** 需要多个逻辑步骤
- **分析权衡** 不同方法之间
- **规划多步骤实现** 具有依赖关系
- **调试复杂问题** 需要系统分析
- **做出架构决策** 具有多个考虑因素

## 示例用法

### 没有思考工具

`> 为我们的 API 实现缓存的最佳方法是什么？

我建议使用 Redis 来缓存您的 API 响应...
`

### 有思考工具

`> 为我们的 API 实现缓存的最佳方法是什么？

🧠 思考中...

让我考虑一下缓存需求：

1. 首先，我需要考虑被缓存的数据类型
   - API 响应表明读取密集型工作负载
   - 需要处理缓存失效

2. 评估缓存解决方案：
   - 内存缓存（快速但受 RAM 限制）
   - Redis（分布式、持久化、功能丰富）
   - Memcached（简单、快速，但功能较少）

3. 考虑您的用例：
   - API 响应受益于分布式缓存
   - 需要 TTL 支持自动过期
   - 更新时可能需要缓存失效

4. Redis 似乎最好，因为：
   - 支持复杂数据结构
   - 内置 TTL 和驱逐策略
   - 可以跨节点分布
   - 如果需要可以持久化

基于此分析，我建议使用 Redis 来缓存您的 API 响应...
`

## 好处

### 用于学习

- **理解推理模式**：看复杂问题如何被分解
- **学习问题解决方法**：观察系统分析
- **识别逻辑缺口**：发现推理可能存在缺陷的地方

### 用于调试

- **跟踪决策路径**：理解为什么做出某些推荐
- **验证假设**：检查 AI 的假设是否与您的上下文匹配
- **及早发现错误**：在实现之前发现逻辑错误

### 用于复杂任务

- **跟随多步骤计划**：看复杂任务如何分解
- **理解依赖关系**：识别步骤之间的关系
- **验证方法**：确认推理与您的目标一致

## 用例

### 架构决策

`> 我们应该为新项目使用微服务还是单体？

🧠 思考中...

让我分析这个架构决策：

1. 要考虑的项目特征：
   - 团队规模和结构
   - 预期的规模和增长
   - 部署需求
   - 开发速度需求

2. 微服务优势：
   - 独立扩展
   - 技术灵活性
   - 故障隔离
   - 但：增加复杂性、运维开销

3. 单体优势：
   - 部署更简单
   - 更容易调试
   - 运维成本更低
   - 但：扩展限制、紧密耦合

4. 决策因素：
   - 小团队 → 单体可能更好
   - 不明确的需求 → 从单体开始
   - 需要快速迭代 → 单体初期更快
   - 如果需要，以后可以重构为微服务

基于此分析...
`

### 算法选择

`> 我应该为这些数据使用什么排序算法？

🧠 思考中...

让我考虑排序需求：

1. 数据特征：
   - 数据集大小
   - 数据是否部分排序？
   - 内存限制
   - 稳定性要求

2. 算法选项：
   - 快速排序：平均 O(n log n)，最坏 O(n²)
   - 归并排序：保证 O(n log n)，稳定
   - 堆排序：O(n log n)，原地
   - Tim 排序：针对现实世界数据优化

3. 权衡：
   - 如果数据部分排序 → Tim 排序表现出色
   - 如果内存有限 → 堆排序（原地）
   - 如果稳定性重要 → 归并排序或 Tim 排序
   - 对于一般情况 → 快速排序通常最快

4. 推荐取决于...
`

### 调试复杂问题

`> 我的应用程序很慢但我不知道为什么

🧠 思考中...

让我系统地分析潜在的性能问题：

1. 常见的性能瓶颈：
   - 数据库查询（N+1 问题、缺少索引）
   - 网络延迟（API 调用、外部服务）
   - 内存问题（泄漏、过度分配）
   - CPU 密集型操作（复杂计算）

2. 诊断方法：
   - 首先，分析以识别热点
   - 检查数据库查询模式
   - 监控网络请求
   - 分析内存使用模式

3. 基于典型模式的最可能原因：
   - 数据库查询通常占慢速的 60-80%
   - 应该在优化代码之前从那里开始

4. 推荐的调查顺序...
`

## 配置

### 启用/禁用

```bash
# 启用
kiro-cli settings chat.enableThinking true

# 禁用
kiro-cli settings chat.enableThinking false

# 检查状态
kiro-cli settings chat.enableThinking
```

## 限制

### 性能影响

- **响应较慢**：思考增加了生成响应的时间
- **使用更多令牌**：思考过程消耗额外的令牌
- **输出更长**：响应更冗长

### 何时不使用

- **简单问题**：直接查询不需要思考开销
- **快速迭代**：可能会减慢快速的来回交流
- **明确定义的任务**：当您只需要答案，而不是推理时

## 最佳实践

### 何时启用

- **学习新概念**：理解推荐背后的推理
- **复杂决策**：需要验证决策过程
- **调试**：想看到系统的问题分析
- **代码审查**：理解为什么建议某些方法

### 何时禁用

- **简单任务**：直接的问题不需要推理
- **速度优先**：需要快速响应而无需解释
- **熟悉的领域**：已经理解推理模式

### 工作流集成

1. **为复杂任务启用**：在开始困难问题时开启
2. **从推理中学习**：观察问题如何被分解
3. **为执行禁用**：在实现已知解决方案时关闭
4. **为审查重新启用**：在验证方法时重新开启

## 故障排除

### 思考不出现

1. **验证已启用**：
   
   ```bash
   kiro-cli settings chat.enableThinking
   ```
2. **尝试复杂问题**：简单问题可能不会触发思考
3. **重启聊天会话**：更改可能需要新会话

### 思考太多

如果思考输出令人不知所措：
1. **为更简单的任务禁用**：
   
   ```bash
   kiro-cli settings chat.enableThinking false
   ```
2. **请求简洁的答案**：明确请求简短响应
3. **用于特定问题**：仅在需要时启用
