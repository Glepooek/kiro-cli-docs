# 安全考虑

Kiro 提供了可以修改您的系统和 AWS 资源的强大能力。理解安全含义并遵循最佳实践有助于您安全地使用这些能力。

## 理解安全风险

使用 Kiro 时，请注意以下潜在安全风险:
- 意外的系统更改: Kiro 可能以意想不到的方式解释您的请求，导致意外修改
- AWS 资源修改: 可能创建、修改或删除资源，可能影响生产环境或产生费用
- 数据丢失: 删除或覆盖文件的命令可能导致数据丢失
- 安全漏洞: 命令可能损害系统安全（如果未经适当审查）

使用 /tools trust-all 或 /acceptall 时，这些风险会显著增加，因为它们会绕过确认提示。

风险的具体示例包括:
- "清理旧文件"的请求可能删除重要的配置文件
- "优化我的 EC2 实例"的请求可能终止运行中的实例
- "修复安全问题"的请求可能以暴露敏感数据的方式修改权限

> **警告**
>
> 不要在生产环境中使用 `/tools trust-all` 或 `/acceptall` 模式，或在处理敏感数据或资源时使用。您对 Kiro 执行的所有操作负责。

## 通用安全最佳实践

在任何环境中使用 Kiro 时，特别是那些包含敏感文件、私钥、令牌或其他机密信息的环境，请考虑实施这些安全措施:

### 限制文件访问

默认情况下，Kiro 可以读取文件而无需每次请求权限（Read 默认受信任）。对于敏感环境，您可以限制此行为:

```bash
/tools untrust read
```

使用此设置，Kiro 将在读取任何文件之前请求您的明确权限。这使您可以细粒度控制 Kiro 在会话期间可以访问哪些文件。

### 额外安全措施

对于包含高度敏感信息的环境，考虑这些额外措施:
- 在不包含敏感凭据或数据的专用开发环境中使用
- 将敏感文件存储在项目目录之外或具有受限权限的位置
- 使用环境变量存储敏感值，而不是硬编码在文件中
- 考虑使用 `/tools untrust aws` 在进行 AWS API 调用之前要求明确权限
- 使用 steering 定义安全指南和限制

### 安全使用 /tools trust-all

如果您必须为特定工作流程使用 `/tools trustall` 或 `/acceptall`，请遵循这些安全实践以最小化风险:
- 仅在开发或测试环境中使用，切勿在生产环境使用
- 仅在特定任务期间启用 `/tools trust-all`，然后立即使用 `/tools reset` 禁用以返回默认权限
- 在启用 `/tools trust-all` 之前备份重要数据
- 在启用 `/tools trust-all` 时使用具有最小权限的 AWS 凭证
- 在启用 `/tools trust-all` 时仔细监控 Kiro 代理采取的所有操作

要在使用 /tools trust-all 后返回默认权限设置，使用 reset 命令:

```bash
/tools reset
```

这将所有工具恢复为其默认权限级别，仅 Read 默认受信任。
